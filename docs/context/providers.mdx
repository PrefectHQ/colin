Providers connect Colin templates to external data sources. A provider handles a specific type of integration—fetching resources from MCP servers, calling language models, or reading from APIs. Each provider exposes functions you call directly in your templates.

Providers return domain objects with `.content` and metadata. You can use these objects directly or wrap them with `ref()` to track dependencies in the manifest.

## HTTP Provider

The HTTP provider fetches content from web URLs. It's a builtin—no configuration needed.

```markdown
{{ http.get('https://api.example.com/data.json') }}
```

URLs without a scheme default to `https://`:

```markdown
{{ http.get('example.com/api/users') }}
```

The function returns an `HTTPResource` with `.content`, `.uri`, and `.content_type` properties:

```markdown
{% set response = http.get('https://api.example.com/status') %}

{{ response.content }}

Content-Type: {{ response.content_type }}
```

## MCP Provider

The MCP provider connects to Model Context Protocol servers. Configure servers in `colin.toml`, then access them in templates as `mcp.<name>`:

```toml colin.toml
[[providers.mcp]]
name = "github"
command = "uvx"
args = ["mcp-server-github"]

[[providers.mcp]]
name = "linear"
command = "npx"
args = ["@linear/mcp-server"]
```

Each MCP server requires a `name`. This name becomes the accessor in templates.

### Reading Resources

Use `mcp.<name>.resource()` to fetch content:

```markdown
{{ mcp.github.resource('repo://owner/repo/README.md') }}
{{ mcp.linear.resource('projects?team=engineering') }}
```

This returns an `MCPResource` object with `.content`, `.name`, and `.uri` properties.

### Using Prompts

Some MCP servers provide prompt templates:

```markdown
{% set review = mcp.github.prompt('code-review', repo='owner/repo') %}
{{ review.content }}
```

### Accessing Metadata

Provider functions return domain objects, not raw strings. Access the content and metadata directly:

```markdown
{% set resource = mcp.github.resource('repo://owner/repo/README.md') %}

{{ resource.content }}

Name: {{ resource.name }}
URI: {{ resource.uri }}
```

## Dependency Tracking

By default, provider function calls are not tracked as dependencies. To record a dependency in the manifest, wrap the result with `ref()`:

```markdown
{# Not tracked #}
{{ mcp.github.resource('repo://...').content }}

{# Tracked as a dependency #}
{{ ref(mcp.github.resource('repo://...')).content }}
```

When you use `ref()`, Colin records the resource in `refs_evaluated`. Changes to tracked dependencies trigger recompilation of dependent documents.

The wrapped result is a `RefResult`. Access the original domain object via `.source`:

```markdown
{% set tracked = ref(mcp.github.resource('repo://owner/repo/README.md')) %}

{{ tracked.content }}
{{ tracked.source.uri }}
```

See [References](/projects/references#referencing-provider-objects) for more details.

## Configuring MCP Servers

MCP servers are configured under `[[providers.mcp]]` in `colin.toml`. See [Configuration](/running/configuration#mcp-servers) for complete options including environment variables, remote servers, and authentication.

Basic configuration:

```toml colin.toml
[[providers.mcp]]
name = "github"
command = "uvx"
args = ["mcp-server-github"]
env = { GITHUB_TOKEN = "${GITHUB_TOKEN}" }
```

| Field | Description |
| :---- | :---------- |
| `name` | Required. Identifier used in templates as `mcp.<name>` |
| `command` | Executable to run (for stdio servers) |
| `args` | Command-line arguments |
| `env` | Environment variables passed to the server |
| `url` | Server URL (for remote servers) |
| `headers` | HTTP headers (for remote servers) |

## Creating Custom Providers

Providers extend the `Provider` base class. Each provider declares which URI schemes it handles via the `schemes` attribute and implements an async `read()` method that returns content as a string.

### Resource Lifecycle

Providers that manage stateful resources—database connections, HTTP clients, API sessions—override the `lifespan()` method. This is an async context manager that Colin enters at startup and exits at shutdown. Set up your resources before the `yield`, and they'll be cleaned up automatically when the context exits.

```python
@asynccontextmanager
async def lifespan(self) -> AsyncIterator[None]:
    async with httpx.AsyncClient() as client:
        self._client = client
        yield
```

Resources are created eagerly when Colin starts, not lazily on first use. This surfaces connection errors early and ensures consistent behavior. Providers without resources to manage inherit a default `lifespan()` that does nothing.

### Template Functions

To expose functions in templates, override `get_functions()` and return a dictionary mapping function names to async callables. A provider with `schemes = ["myscheme"]` that returns `{"fetch": self._fetch}` becomes accessible as `myscheme.fetch()` in templates.
