A Colin document is a Markdown file that can contain Jinja templating. Documents form the building blocks of your context graph, and each one compiles to a standalone output that can reference and incorporate content from other documents.

Documents live in your project's `models/` directory (or whatever you configure as `model-path` in `colin.toml`). When you run `colin run`, Colin discovers all `.md` files in this directory and compiles them based on their dependencies.

## File Structure

Every document consists of two parts: optional YAML frontmatter followed by the document body.

```markdown models/company.md
---
name: Company Overview
description: Core information about our company
---

Acme Corp builds developer tools that streamline CI/CD pipelines.
Founded in 2020, we serve over 500 enterprise customers.
```

The frontmatter defines metadata about the document. The body contains Markdown content, optionally enhanced with Jinja templating for dynamic behavior.

## Frontmatter

Frontmatter is optional. When present, it's YAML wrapped in `---` markers at the top of the file:

```yaml
---
name: Product Brief
description: Summary of product capabilities for sales team
---
```

Two fields are particularly useful:

**`name`** - A human-readable identifier for the document. When omitted, Colin derives the name from the filename.

**`description`** - Explains what this document contains. This metadata travels with the document when referenced, helping LLMs understand context.

Documents without frontmatter work fine—Colin infers the name from the filename and leaves other metadata empty. This is useful for simple content files or when you're referencing non-Markdown sources.

Project-level configuration (paths, MCP servers) belongs in `colin.toml`. See [Configuration](/running/configuration) for details.

## Document Settings

The `colin:` block in frontmatter controls document-specific compilation behavior:

```yaml
---
name: Market Analysis
colin:
  cache:
    policy: auto
    expires: 1M
---
```

### Cache Policy

The cache policy controls when a document gets recompiled:

| Policy | Behavior | Rebuilds when |
| :----- | :------- | :------------ |
| `auto` | Smart caching (default) | Refs change or time expires |
| `always` | Aggressive caching | `--no-cache` only |
| `never` | No caching | Every run |

```yaml
colin:
  cache: never  # Always rebuild
```

Use `never` for documents that incorporate live data or timestamps. Use `always` for expensive operations where the output doesn't change.

For shorthand, you can specify just the policy value:

```yaml
colin:
  cache: always
```

### Expiration Threshold

The `expires` setting defines when a document becomes stale based on time elapsed since last compilation:

```yaml
colin:
  cache:
    expires: 1d  # Rebuild after 1 day
```

Supported duration formats:

| Format | Meaning | Example |
| :----- | :------ | :------ |
| `Nm` | N minutes | `30m` |
| `Nh` | N hours | `24h` |
| `Nd` | N days | `7d` |
| `Nw` | N weeks | `2w` |
| `NM` | N calendar months | `1M`, `3M` |
| `NQ` | N calendar quarters | `1Q` |

Months and quarters use calendar-aware arithmetic. For example, `1M` after January 31st is February 28th (or 29th), not "30 days later."

### Calendar-Aligned Expiration

For expiration based on calendar boundaries rather than elapsed time, use the `c` prefix:

```yaml
colin:
  cache:
    expires: 1cM  # Rebuild when calendar month changes
```

| Format | Meaning | Boundary | Valid N |
| :----- | :------ | :------- | :------ |
| `Ncm` | Every N minutes | :00, :15, :30, :45 etc. | Divides 60 |
| `Nch` | Every N hours | 00:00, 06:00, 12:00 etc. | Divides 24 |
| `1cd` | New calendar day | Midnight | 1 only |
| `1cw` | New calendar week | Monday midnight (ISO) | 1 only |
| `NcM` | Every N months | 1st of month | Divides 12 |
| `NcQ` | Every N quarters | Start of quarter | Divides 4 |

Calendar-aligned values must divide evenly into their containing period. For example, `30cm` creates boundaries at :00 and :30, while `15cm` creates boundaries at :00, :15, :30, and :45. Use `2cM` for bimonthly updates or `2cQ` for semiannual updates.

A document compiled on January 31st with `expires: 1cM` expires on February 1st at midnight—when the calendar month changes—regardless of how much time has passed. With `expires: 1cQ`, a document compiled any time in Q1 (Jan-Mar) expires at the start of April 1st.

### Cache Invalidation

A document is considered stale and recompiles if **any** of these conditions are true:
- The source file changed
- Any referenced document was updated more recently
- The expiration threshold (if set) has been exceeded

When a document recompiles, all documents that reference it also recompile to pick up the changes.

## Jinja Templating

The document body supports standard Jinja2 templating syntax. This enables dynamic content through expressions, filters, and control structures.

### Expressions

Use double braces to output values:

```markdown models/status.md
---
name: Project Status
---

# Project Status

Last updated: {{ now().strftime('%Y-%m-%d') }}
```

### Control Structures

Standard Jinja control flow works in documents:

```markdown models/team-roster.md
---
name: Team Roster
---

# Team

{% for member in ['Alice', 'Bob', 'Charlie'] %}
- {{ member }}
{% endfor %}
```

### Filters

Filters transform values using the pipe syntax:

```markdown models/summary.md
---
name: Summary
---

{{ ref('report').content | upper }}
```

Colin provides special LLM-powered filters like `extract()` for intelligent content transformation. See the [Context](/context/overview) documentation for details on available filters.

## LLM Blocks

For complex transformations, use `{% llm %}` blocks to invoke LLM processing:

```markdown models/analysis.md
---
name: Competitive Analysis
---

# Analysis

{% llm %}
Compare these two products and identify key differentiators:

Product A: {{ ref('product-a').content }}
Product B: {{ ref('product-b').content }}

Focus on pricing, features, and target market.
{% endllm %}
```

The content inside the block becomes the prompt. Colin sends it to the configured LLM and replaces the block with the response. LLM calls are cached by input hash, so unchanged prompts return cached results on subsequent compiles.

You can specify a model override:

```markdown
{% llm model="anthropic:claude-sonnet-4-5" %}
Summarize this content for an executive audience.
{% endllm %}
```

## Section Blocks

Named sections let you mark and reference specific parts of a document from other templates. This is useful for creating modular documents where different sections can be accessed independently:

```markdown models/plan.md
---
name: Strategic Plan
---

{% section strategy %}
## Our Strategy
Focus on growth through innovation and customer success.
Target enterprise market with AI-powered solutions.
{% endsection %}

{% section "key metrics" %}
## Key Metrics
- Revenue: $1M ARR
- Customers: 50 enterprise
- Team size: 12
{% endsection %}
```

Access sections from other documents using `ref()`:

```markdown models/summary.md
---
name: Executive Summary
---

## Strategy Overview
{{ ref('plan.md').sections.strategy }}

## Performance
{{ ref('plan.md').sections['key metrics'] }}
```

Section names support both identifiers (`strategy`) and quoted strings (`"key metrics"`). Use quoted strings for names with spaces or special characters.

**Dot access**: `ref('doc').sections.name` (for simple identifiers)
**Dict access**: `ref('doc').sections['name']` (for any name, including spaces)

### Format-Aware Sections

Sections automatically adapt to your output format:

- **Markdown output**: Returns raw string content
- **JSON/YAML output**: Parses markdown structure into data (headers → keys, lists → arrays)

For a document with `colin.output: json`, section content is parsed:

```markdown models/config.json.md
---
colin:
  output: json
---

{% section database %}
## host
localhost

## port
5432
{% endsection %}
```

Accessing `ref('config.json.md').sections.database` returns:
```json
{
  "host": "localhost",
  "port": 5432
}
```

### Section Naming

- **Duplicate names**: If multiple sections have the same name, the last one wins
- **Empty sections**: Sections can be empty (useful for placeholders)
- **Special characters**: Use quoted strings for names with spaces, hyphens, or other characters

## Defer Blocks

Defer blocks let documents reference their own rendered output. Use `{% defer %}` when you need content based on the complete rendered document—table of contents, metadata, summaries, or change tracking.

```markdown models/guide.md
{% defer %}
## Table of Contents
{% for name in rendered.sections.keys() %}
- [{{ name | title }}](#{{ name }})
{% endfor %}
{% enddefer %}

{% section introduction %}
## Introduction
Welcome to the guide.
{% endsection %}
```

### How It Works

Two-pass rendering: first pass renders the document and stores defer blocks, second pass renders defer blocks with access to `rendered` and `previous_rendered`.

### Accessing Rendered Output

Defer blocks have access to two variables:

#### Content

`rendered.content` - Full rendered text as string
`previous_rendered.content` - Previous version's text (or `None` on first compile)

```markdown
{% defer %}
Words: {{ rendered.content.split() | length }}
{% if previous_rendered %}
Changed: {{ rendered.content | length - previous_rendered.content | length }} chars
{% endif %}
{% enddefer %}
```

#### Sections

`rendered.sections` - Format-aware accessor for sections (raw strings for markdown, parsed data for JSON/YAML)
`previous_rendered.sections` - Previous version's sections

```markdown
{% defer %}
{% for name in rendered.sections.keys() %}
- {{ name | title }}
{% endfor %}
{% enddefer %}
```

#### Previous Rendered

`previous_rendered` is `None` on first compile and contains the cached output from the last compile on subsequent runs.

### Variables from First Pass

Variables defined outside defer blocks are accessible inside:

```markdown
{% set title = "Strategic Plan" %}

{% defer %}
Title: {{ title }}
Word count: {{ rendered.content.split() | length }}
{% enddefer %}
```

### Common Patterns

#### Auto-Generate Metadata

```yaml
---
name: {% defer %}{{ rendered.content | llm_extract("A concise title") }}{% enddefer %}
tags: {% defer %}{% llm %}Suggest 3-5 tags: {{ rendered.content }}{% endllm %}{% enddefer %}
---
```

#### Table of Contents

```markdown
{% defer %}
## Contents
{% for name in rendered.sections.keys() %}
- [{{ name | title }}](#{{ name | replace(' ', '-') }})
{% endfor %}
{% enddefer %}
```

#### Executive Summary

```markdown
{% defer %}
{% llm %}Summarize in 2-3 sentences: {{ rendered.content }}{% endllm %}
{% enddefer %}
```

#### Change Tracking

```markdown
{% defer %}
{% if previous_rendered %}
Changed: {{ rendered.content | length - previous_rendered.content | length }} chars
{% else %}
First version
{% endif %}
{% enddefer %}
```

### Multiple Defer Blocks

Multiple defer blocks in a document each see the same first-pass output but not each other's output.

### Sections in Defer Blocks

Defer blocks can define sections that are captured in document metadata:

```markdown
{% defer %}
{% section summary %}
## Summary
{{ rendered.sections.keys() | list | length }} sections total
{% endsection %}
{% enddefer %}
```
